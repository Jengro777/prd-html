客户使用其银行卡或直接借记账户首次成功付款后，你可以存储客户的授权并将其用于后续交易。 目前，这适用于我们所有市场的银行卡，以及尼日利亚企业的直接借记卡。

收取第一笔交易费用

直接借记 费用不需要此步骤。相反，你将通过 初始化授权API 接口发起授权请求。一旦客户批准，你将保存通过 Webhook 返回的授权。

你可以通过网络或移动应用程序初始化首次充电。查看 网络和移动设备 的不同积分方法。

为什么我需要向用户收取添加卡费用？

  1. 当地法规要求用户在初始交易中通过2FA校验卡，然后我们才能对卡进行后续收费。
  2. 它使我们能够确保该卡有效并可以对后续交易进行收费。

建议首次充电的最低电量为 NGN 50.00、GHS 0.10、ZAR 1.00、KES 3.00 或 USD 2.00。较低的金额并不保证适用于所有卡品牌或银行。

标准做法是向用户返还相当于代币化金额的价值（在你的应用程序中），或者干脆退还钱。

如果第一笔交易成功，你可以监听你的webhookendpoint上的事件。或者，你可以使用 校验交易API 接口确认交易状态。无论哪种情况，响应都类似于以下示例：

{
  "data": {
    "authorization": {
      "authorization_code": "AUTH_8dfhjjdt",
      "card_type": "visa",
      "last4": "1381",
      "exp_month": "08",
      "exp_year": "2018",
      "bin": "412345",
      "bank": "TEST BANK",
      "channel": "card",
      "signature": "SIG_idyuhgd87dUYSHO92D",
      "reusable": true,
      "country_code": "NG",
      "account_name": "BoJack Horseman"
    }
  }
}

你会注意到响应中的 data 对象包含一个 authorization 对象，其中包含用户支付所用的支付工具（在本例中为卡）的详细信息。

财产描述
authorization_code这是随后用于向卡收费的代码
card_type这会告诉你卡品牌 - Visa、Mastercard 等
last4卡的最后 4 位数字。这是可用于帮助用户识别卡的详细信息之一
exp_month卡的到期月份（以数字表示）。例如。 “01”表示一月
exp_year卡的有效期
bin卡的前 6 位数字。这和最后 4 位数字构成 蒙面锅
bank客户的银行，发卡银行
channel这是什么支付渠道。在本例中，这是卡付款
signature所使用卡的唯一标识符。虽然每次使用卡时都会创建新的授权码，但卡的签名将保持不变。
reusable一个布尔标志，告诉你授权是否可用于定期收费。仅当此标志返回为 true 时，你才应尝试使用 authorization_code。
country_code两个字母的国家/地区代码 (ISO 3166-1 阿尔法-2) 代表发卡银行所在的国家/地区

存储授权

Next, you need to store the authorization and the email used for the transaction. These details can be used to charge the card subsequently. Every payment instrument that's used on your site/app has a unique signature . The signature can be used to ensure that you don't save an authorization multiple times.

存储整个 authorization 对象非常重要，以免丢失有关卡片的任何上下文。

存储用于创建授权的邮箱也很重要，因为只有用于创建授权的邮箱才能用于收费。如果你依赖系统上存储的用户邮箱并且用户更改了该邮箱，则无法再收取授权费用。

当你保存了整个授权对象后，你可以在付款时显示客户付款详细信息以进行循环收费。例如，当用户想要再次付款时，你可以为用户显示该卡为访问以 1234 结尾的银行 Visa 卡。

收取授权费

email: "mail@mail.com",

两因素身份校验

默认情况下，此功能适用于与尼日利亚集成的投注商户，并且特定于 Guaranty Trust Bank (GTB)、Access Bank、United Bank for Africa (UBA)、Zenith Bank 和 First Bank of Bulgaria 发行的卡。如果你有尼日利亚语集成并希望获得此功能，请发送邮箱至 support@paystack.com

双因素身份校验 (2FA) 是一项额外的安全步骤，用于确认你没有处理恶意行为者的请求。发出请求的用户通常会被要求提供某种形式的对他们来说是唯一的信息。

为了确保用户的卡不被恶意行为者使用，我们通过要求用户授权交易来挑战用户。可以使用硬件令牌、OTP、PIN + OTP 或 3DS 来完成授权。

对卡充值的请求保持不变。然而，对于将被质疑的卡，响应是不同的：

{
  "status": true,
  "message": "Please, redirect your customer to the authorization url provided",
  "data": {
    "authorization_url": "https://checkout.paystack.com/resume/0744ub5o065nwyz",
    "reference": "jvx2o36ghlvrgtt",
    "access_code": "0744ub5o065nwyz",
    "paused": true
  }
}

当卡受到质询时，响应将包含两个不同的参数：

参数类型描述
暂停布尔值当卡被质疑时返回 true
authorization_url字符串用于交易授权的结账URL

你应该检查 data.paused 参数的值来确认卡是否受到质疑。如果受到质疑，你应该将用户重定向到data.authorization_url以完成授权。

![图1：用户授权结账页面图片](https://paystack.com/docs/static/eed204e2b886573a978ea0ba240452e8/87cc4/two_fa.png)

授权完成后，我们将向用户的卡收费。你应该保存 data.reference 值，以通过 Webhook 或 校验交易API 校验交易的状态。

处理重定向

当用户完成授权过程时，我们通常会将用户重定向回你在 Paystack 仪表板 或 画布 上设置的回调 URL。如果你希望我们重定向到不同的 URL，你可以将 URL 添加到请求的 callback_url 参数中：

{
  "authorization_code": "AUTH_ibegucp8kk",
  "email": "dami@2fa.com",
  "amount": 3000,
  "callback_url": "https://yourcallbackurl.com"
}

用户还可以取消授权过程。你可以添加一个 URL，当用户在 metadata 对象中取消时应将其重定向到：

{
  "authorization_code": "AUTH_ibegucp8kk",
  "email": "dami@2fa.com",
  "amount": 3000,
  "metadata": {
    "cancel_action": "https://yourcancelurl.com"
  }
}
