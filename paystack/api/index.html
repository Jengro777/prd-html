API 参考

API 简介

了解如何将 Paystack 的 API 集成到你的应用中。

API 基础

通过 Paystack API，你可以用代码完成收款、管理交易，以及在其他场景中通过 Paystack Dashboard 完成的操作。它是一套 RESTful、基于 JSON 的 API，使用标准 HTTP 方法，多数请求都需要鉴权。

所有请求必须通过 HTTPS 发起，不支持未加密的 HTTP 请求。

基础地址（Base URL）

所有 API 请求的基础地址为：

https://api.paystack.co

测试环境与生产环境使用同一个基础地址，具体环境由你使用的 API Key 决定。

环境与 API Key

Paystack 提供测试（Test）与生产（Live）两套环境，各自拥有独立的 API Key。开发与测试阶段使用测试 Key，正式上线使用生产 Key。

关于如何获取与管理 API Key，请参阅下方的认证鉴权章节。

HTTP 方法

Paystack API 遵循标准 HTTP 语义：

方法类型说明
POSTString在服务端创建一个新资源。
GETString获取某个资源的表示。
PUTString更新已有资源；若资源不存在则创建。
DELETEString删除指定的资源。

发起请求

所有请求都发往上述基础地址，并必须在 Authorization 请求头中携带你的私钥（Secret Key）。

请求头格式为：Authorization: Bearer YOUR_SECRET_KEY。

API 参考中为每个接口提供了请求示例，你可以直接复制到自己的代码中，或通过命令行使用 cURL 运行。你也可以使用 Postman 和 Paystack Postman Collection 来探索 API。

请求与响应

请求体与响应数据均为 JSON 格式，响应的 Content-Type 始终是 application/json。总体而言，所有响应都采用如下结构：

statusBoolean

表示你的请求是否成功。建议结合 HTTP 状态码一起判断接口调用结果。

messageString

本次响应及其状态的摘要说明。例如获取客户列表时，message 可能是 “Customers retrieved”。请求出错时，message 会包含具体的错误描述。这个字段在任何请求中都会返回。

dataObject

请求的结果。根据请求类型不同，可能是对象，也可能是数组。例如查询单个客户时，data 中返回一个 customer 对象；查询列表时，data 则是客户数组。

响应格式JSON
{
  "status": "[boolean]",
  "message": "[string]",
  "data": "[object]"
}

meta 对象

许多 Paystack API 响应会包含一个 meta 对象，用于承载接口特有的附加信息。其内容取决于：

  • 请求是成功还是失败；
  • 返回响应的具体接口。

请求成功时，meta 通常包含返回数据的补充信息，这在列表接口中最常见 —— Paystack 会返回额外字段，帮助你在海量数据中翻页遍历。

列表接口中 meta 返回的字段与所使用的分页方式有关。各字段的完整说明，以及何时使用游标分页、何时使用偏移分页，请参阅分页章节。

请求失败时，meta 会包含有助于定位问题的诊断信息。关于错误响应以及如何借助 meta 排查错误，请参阅错误处理章节。

meta 结构JSON
{
  "meta": {
    "total": 2,
    "skipped": 0,
    "perPage": 50,
    "page": 1,
    "pageCount": 1
  }
}

支持的货币

Paystack 遵循 ISO 4217 标准表示货币代码。传递金额时，必须使用该货币的最小单位（subunit）。

以最小单位传递，意味着把基础金额乘以 100。例如客户需要支付 NGN 100，请求中应传 10000 = 100 * 100。

部分市场支持多种货币，每种货币有各自的交易手续费与最低金额。你可以在下表中了解支持的货币，也可以参考《Enabling International Payments》一文。

XOF 没有最小单位，但开发者仍必须将金额乘以 100。这并不表示金额可以有小数部分 —— 如果在处理过程中发现小数部分，我们会忽略它。

货币代码最小单位说明交易最低金额可用地区
NGNKobo尼日利亚奈拉₦ 50.00尼日利亚
USDCent美元$ 2.00肯尼亚、尼日利亚
GHSPesewa加纳塞地₵ 0.10加纳
ZARCent南非兰特R 1.00南非
KESCent肯尼亚先令Ksh. 3.00肯尼亚
XOF-西非法郎XOF 1.00科特迪瓦
金额示例JSON
{
  "amount": 5000,
  "currency": "NGN"
}

认证鉴权

所有发往 Paystack API 的请求都必须经过认证。认证用于识别请求属于哪个 Paystack 集成，并决定它是否有权执行所请求的操作。

Paystack API 使用 API Key 对请求进行认证。每个请求都必须在 Authorization 请求头中携带你的私钥，并使用 Bearer 方案。

API Key

每个 Paystack 集成都为每种环境提供两类 API Key：

类型前缀说明
公钥 Public Keypk_仅用于前端集成 Paystack Inline 以及我们的移动端 SDK。根据设计，公钥只能向你的账户发起交易。
私钥 Secret Keysk_用于后端发起 API 请求。私钥必须安全保存。

你可以在 Paystack Dashboard 的 “API Keys & Webhooks” 页面，或 Paystack Canvas 的 Developers 概览页中找到 API Key。

建议定期轮换 API Key；如果你怀疑私钥已泄露，应立即轮换。轮换时在与查看相同的 Dashboard / Canvas 页面生成新 Key 即可。

不要把私钥提交到 Git 仓库，也不要在前端代码中使用私钥。

Authorization 请求头格式：Authorization: Bearer SECRET_KEY

Authorization: Bearer sk_test_r3m3mb3r2pu70nasm1l3

未认证的 API 请求会返回状态码 401: Unauthorized。所有 API 请求都必须通过 HTTPS 发起。

不要将 VERIFY_PEER 设置为 FALSE。请确保服务器会校验与 Paystack 之间的 SSL 连接。

测试模式与生产模式

Paystack 为集成提供两套相互独立的环境：

  1. 测试模式（Test mode）：用于开发与质量验证，此处的交易和 API 调用不涉及真实资金。
  2. 生产模式（Live mode）：用于正式环境，交易与结算都是真实发生的，并通过你的生产 Paystack 账户处理。

每套环境都有自己的公钥与私钥。测试 Key 的前缀为 pk_test_ 和 sk_test_，生产 Key 的前缀为 pk_live_ 和 sk_live_。

测试环境力求贴近生产环境的表现，但并非所有功能都可用。例如测试模式不会执行结算，部分支付渠道也不可用。

IP 白名单

IP 白名单是一项安全功能，只允许特定 IP 地址使用你的私钥发起 API 请求。它通过阻止来自未知 IP 的私钥调用，为账户增加一层保护。

启用后，Paystack 会针对每个使用私钥的请求校验来源 IP，并拦截不在白名单中的请求。

你可以为每套环境配置最多 10 个 IP 地址，入口位于 Paystack Dashboard 或 Paystack Canvas。只有管理员，或拥有 “管理 API Keys 与 Webhooks” 权限的用户才能配置白名单。当有人更新生产私钥的白名单时，我们会向该集成的主要负责人发送邮件通知。

仅支持合法的公网 IPv4 地址，不支持 IPv6 地址、IP 段以及内网地址。

密钥管理最佳实践

  1. 永远不要把私钥写入前端代码、移动端应用或公开仓库。
  2. 通过环境变量或密钥管理服务安全地保存密钥。
  3. 定期轮换密钥，尤其是在怀疑密钥已泄露时。
  4. 限制 Dashboard 中可以查看或管理 API Key 的人员范围。

请求速率限制

速率限制是我们基础设施中用于保障 API 稳定性的机制之一，用来避免 API 请求量突增。每个接口在每个时间窗口内可发起的请求数是有限的，超过该限制会返回 429 错误，表示需要降低请求频率。

收到 429 时，请解析响应头以决定后续处理方式：

x-ratelimit-resetNumber

以秒为单位的时间，表示当前限流窗口何时结束，也就是你可以重试请求的时间。

x-ratelimit-remainingNumber

当前限流窗口内剩余的可用请求次数。

x-ratelimit-limitNumber

每个限流窗口允许的最大请求次数。

限流响应JSON
{
  "status": false,
  "message": "Rate limit exceeded!",
  "meta": {
    "nextStep": "Wait a few minutes and try the API call again"
  },
  "type": "api_error",
  "code": "rate_limited"
}

默认限额

大多数接口共用同一默认限额。限额按集成维度计算，生产与测试模式各自独立计数。

模式限额
生产 Live每 60 秒 600 次请求
测试 Test每 60 秒 100 次请求

测试模式用于开发与集成联调，不适合做压力测试。

扩展限额

部分基础接口拥有更高的专属限额，以保障关键业务流程顺畅运行，包括：

接口限额
交易校验 Verify Transaction每 60 秒 3,000 次请求
解析账号 Resolve Account Number每 60 秒 1,500 次请求
初始化交易 Initialize Transaction每 60 秒 1,200 次请求
授权扣款 Charge Authorization每 60 秒 1,200 次请求
创建扣款 Create Charge每 60 秒 1,200 次请求
查询待处理扣款 Check Pending Charge每 60 秒 1,200 次请求
发起转账 Initiate Transfer每 60 秒 900 次请求

扩展限额仅适用于生产模式；测试模式下所有接口都使用默认限额。

处理 429

当接口返回 429 时，你的集成应当：

  1. 从响应头中读取 x-ratelimit-reset 的值（单位：秒）。
  2. 在该窗口结束前暂停对该接口的请求。
  3. 如果多个接口持续返回 429，请先暂停并排查 —— 通常原因是未受控的循环调用。

限额按接口计算，而不是按整个集成计算。当某个接口被限流时，其他接口仍会正常返回，直到它们各自触达限额。

如何避免触达限额

实践中，多数限流问题都来自几种可避免的调用模式。为避免触达限额：

  1. 用 Webhook 代替轮询。最常见的 429 来源，是在发起异步请求后立即轮询。例如在等待最终交易状态时循环调用 /transaction/verify/:reference。对于异步请求我们会发送 Webhook 事件。如果必须主动校验，请控制为每次请求一次。
  2. 缓存稳定的查询结果。对于相同的账号与银行代码，/bank/resolve 除客户在银行侧变更了信息外，返回的户名始终一致。缓存这类数据同时也能提升应用性能。
  3. 对账时批量拉取。对账时使用 /transaction 列表接口配合时间范围，而不是逐个 reference 调用校验接口。列表请求默认返回 50 条。
  4. 高频场景使用批量接口。如果需要发起大量转账或扣款，请使用批量转账和批量扣款接口，而不是在循环中调用单笔接口。每次批量请求只计一次限额，却能处理一批数据。

自定义限额

部分业务具有较高的吞吐量且调用模式难以预测。如果你需要更高的限额，请发送邮件至 support@paystack.com，说明涉及的接口、预期的稳定与峰值请求速率，以及你的集成用途简介，我们会与你一起配置合适的限额。

分页与遍历

分页让你可以高效地从 Paystack API 获取大规模数据。一次性返回全部结果会较慢且消耗资源，分页会先把数据切成较小的批次再返回，从而提升性能、降低网络负载，并改善处理大数据集时的整体体验。

Paystack API 支持两种分页方式：

  1. 偏移分页（Offset Pagination）
  2. 游标分页（Cursor Pagination）

两种方式各有适用场景与实现细节。

偏移分页

偏移分页允许你在获取记录时指定具体的 page 与 perPage 值。page 指定要获取第几页记录，perPage 指定每页返回多少条记录。

使用时，把 page 和 perPage 作为查询参数放入请求：

pageNumber

要获取的页码。

perPageNumber

每次请求返回的记录数。默认值：50

GET /transaction 返回的 JSON 中，meta 对象包含 total_volume 参数，表示已获取交易金额的总和。

偏移分页请求cURL
#!/bin/sh
url="https://api.paystack.co/transaction?page=1&perPage=50"
authorization="Authorization: Bearer YOUR_SECRET_KEY"

curl "$url" -H "$authorization" -X GET
偏移分页 metaJSON
{
  "meta": {
    "total": 7316,
    "total_volume": 397800,
    "skipped": 0,
    "perPage": 50,
    "page": 1,
    "pageCount": 147
  }
}

游标分页

游标分页使用一个称为游标（cursor）的唯一标识，记录在数据集中继续读取的位置。它更适合获取大规模数据集，并且在数据频繁新增或删除时结果更稳定。

使用时，在首次请求中加入查询参数 use_cursor 并设为 true。响应中的 meta 对象会包含 next（下一页记录的游标）和 previous（上一页游标）。把它们作为查询参数带入后续请求，即可获取上/下一页数据。

use_cursorBoolean

设为 true 时使用游标分页获取结果。

nextString

分页游标，指向数据集的下一页。填入上一次请求 meta 中返回的 next 游标。

previousString

分页游标，指向数据集的上一页。填入上一次请求 meta 中返回的 previous 游标。

perPageNumber

每次请求返回的记录数。默认值：50

基于游标的分页目前仅在以下接口可用：

  • 交易 Transactions
  • 客户 Customers
  • 专属虚拟账户 Dedicated Accounts
  • 转账收款人 Transfer Recipient
  • 转账 Transfers
  • 争议 Disputes
游标分页请求cURL
#!/bin/sh
url="https://api.paystack.co/transaction?use_cursor=true&perPage=50"
authorization="Authorization: Bearer YOUR_SECRET_KEY"

curl "$url" -H "$authorization" -X GET
游标分页 metaJSON
{
  "meta": {
    "next": "dW5kZWZpbmVkOjQwOTczNTgxNTg=",
    "previous": "null",
    "perPage": 49
  }
}

最佳实践

  1. 选择合适的分页方式：数据量较小且相对静态时使用偏移分页；数据量大或更新频繁时优先使用游标分页。
  2. 设置合理的每页条数：从默认的每页 50 条开始，按实际需要调整，但不要一次性请求超过 1000 条，以免出现性能问题。
  3. 处理边界情况：始终判断是否还有下一页。偏移分页建议持续翻页直到没有结果返回；游标分页在 next 游标缺失时表示已到末尾。
  4. 做好错误处理：准备好处理与分页相关的错误，例如无效的页码或游标。
  5. 关注限流：实现分页时注意 Paystack 的速率限制，尤其是需要拉取大量数据时；必要时在请求之间加入适当的延迟。
  6. 合理使用缓存：如果缓存了分页结果，请确保缓存失效策略能应对数据集的变化。

遵循这些实践，你就能在 Paystack API 上高效处理大数据集，同时为你的用户提供流畅体验。

错误处理

当请求 Paystack API 失败时，响应总会明确说明出了什么问题以及如何修正。每个错误都遵循一致的结构，包含人类可读的 message、机器可读的 code，以及可选的诊断信息，帮助你快速定位问题。

Paystack API 是 RESTful 的，因此使用常规 HTTP 响应码表示请求成功或失败。

状态码说明
200请求成功并完成了预期操作。注意：扣款或校验请求总会返回 200，请检查 data 对象以确认扣款结果（成功或失败）。
201资源创建成功。
400发生校验错误或客户端错误，请求未被处理。
401请求未通过鉴权。可能是 authorization 头中传入了无效私钥，或未传私钥。
404请求的资源不存在，无法完成请求。
5xx因 Paystack 侧错误导致请求无法完成。这不应发生，如遇到请尽快反馈给我们。

错误响应结构

每个错误响应都包含相同的顶层字段：

statusBoolean

表示发往 API 的请求是否被成功接收并处理。建议结合 HTTP 状态码一起判断接口调用结果。

messageString

对所发生错误的简要描述。

metaObject

错误相关的附加信息，其中 next_step 建议了你应采取的下一步操作，也可能包含其他诊断信息，帮助你排查问题。

typeString

错误类型，可能为 api_error、validation_error 或 processor_error。

codeString

Paystack 定义的错误码，用于对错误分类，帮助你快速识别错误类型。

dataObject

错误响应通常不返回该字段；但当错误与被处理的数据相关时，某些场景会返回。

meta 对象包含有助于解决该错误的附加信息，一般会提供 next_step（建议的下一步操作），也可能包含其他用于排障的诊断信息。

例如当批量转账被拒绝时，meta 对象会指出是否存在无效或被列入黑名单的收款人。

校验错误示例JSON
{
  "status": false,
  "message": "Email Address is required",
  "meta": {
    "nextStep": "Provide all required params"
  },
  "type": "validation_error",
  "code": "missing_params"
}
不知道该查哪里？把错误信息或关键词输入页面顶部的搜索框。如果仍未找到需要的答案，欢迎联系我们。

错误分类

错误按类别分组，便于理解以及在代码中分支处理。

api_errorString

表示错误发生在 Paystack API 侧，例如集成了访问未获授权的资源，或其他 API 层面的问题。

validation_errorString

表示错误与请求中的数据无效有关，例如传入的参数缺失或非法。

processor_errorString

表示错误与支付处理方或网关有关，例如余额不足、卡片被冻结或过期，以及支付处理方反馈的其他问题。
